# 炉石制造 / Card Game：工程整改与开发总计划 v1

**任务负责人：项目所有者。适用执行者：本聊天、Sol、后续 Codex。**

本计划以《卡牌游戏记录_v0.5》、视觉施工方案 v1.0、补充接力 v1.1，以及本聊天随后明确的用户决定为依据。它是工程执行与接力规范，不替代原始卡牌记录，不擅自补全规则。

本批为“地图重制前的工程基线整改”。保留当前获准哥特战场原图与正式卡背，不生成图片，不重制地图，不实现左右机关最终美术，不开始卡牌正面 A～H。用户允许整理不合理编码与失效模块，但不授权改平衡或补未知规则。

基准 main：`02e630d2f008b65d362089d7bcc55a157449ac62`。工作分支：`refactor/engineering-baseline-v1`。恢复点：`6d2fcaa7300f074f6853dcdd3fbdb6aa8c4c2e97`。基线测试原有29项。本批完成范围以最终验收报告为准；提交、构建或截图存在，均不自动等于用户已验收。

旧0-7.2B的CSS假凹槽已被用户否决。旧文档中的“完成并锁定”只反映当时错误汇报，不是继续保留黑块的授权。

## 2. 产品边界与不可回退要求

- 经典模式忠实电子化原纸牌：共享总牌库、热座对战；电脑对手仍是目标，不把当前无AI版本写成已支持人机。
- 当前是固定视角的2D分层/贴图战场。未来可以用精灵、动画、粒子或局部滤镜扩展，不需要整个战场转动，不引入完整3D引擎。
- 保留已认可的区域关系：敌方英雄上方、敌我各5个逻辑位、场景居中、牌库左、结束回合右、己方英雄在手牌上方、手牌默认收起。新对局/全屏/安装留右上，除另有明确授权不得删除。
- 战场允许完整高质量原图；禁止再用CSS/DOM/SVG重画石墙、雕像、火盆、旗帜。卡牌正面仍必须是结构化组件、独立透明美术、动态数值、品质效果层，不整张贴概念图。
- 卡背采用最后平整上下边缘的深红裂环定版，无文字、字母。禁止重新生成徽记或恢复伸出卡牌的长尖角。
- 左侧牌库最多4层抽象厚度；大量牌不随真实张数无限堆高；最后4张才逐张减少，0张为空槽。小铭牌显示精确数量。
- 左右机关属于一次共同母版设计与一次整体接入，不再右边独立返工完再重画左边。一次设计不等于只能导出一个文件。
- 讨论、审查、改代码、出图分别授权。“这个看不到/为什么卡住/你觉得如何”不属于生成图片请求。

## 3. 工程分层及所有权

### 3.1 规则层 `src/core/`

规则只接收状态、卡牌目录、命令/参数，返回结果；不得访问DOM、localStorage、计时器或浏览器事件。所有伤害、扣血、死亡、亡语、目标选择回到同一规则管线。

`commands.ts` 是浏览器游戏操作入口；`basic-game.ts` 暂时保留现有规则主体；`deathrattle-effects.ts` 仅解析已支持的亡语表达；`unit-targeting.ts` 负责目标范围/嘲讽；`sacrifice-placement.ts` 不再使用临时第6格。未知效果不得被解析器“猜成”相似技能。

### 3.2 应用层 `src/application/`

`GameStore` 是同页唯一游戏状态持有者。界面只读快照；命令在草稿上执行，失败不提交，成功一次提交、一次持久化、一次通知。读快照被修改不影响真实状态。版本号和时间戳单调推进；保存失败保留内存对局并提示，不能显示虚假的“已保存”。

迁移只导入同一对局尚未完成的旧目标队列，不扫描文字日志重演历史死亡。原v1存档和备份保留兼容。跨标签页使用真实storage事件，不伪造同页StorageEvent；执行命令前检查更新，减少旧窗口覆盖新状态的风险。这不是多人联机事务系统，仍以单设备单窗口游戏为主。

### 3.3 界面层 `src/web/`

`app.ts` 是唯一启动入口；`game-catalog.ts` 统一加载卡牌目录；`session-runtime.ts` 连接存储和命令。手牌、攻击拖拽、献祭、目标弹窗只收集用户意图与展示结果，禁止自己扣血或处理死亡。

显式渲染通知替代全树MutationObserver循环。原型视觉模块可暂时保留，但不得绕过GameStore或重新扫描文本反推规则。牌面数据使用稳定cardId/instanceId，不以可见名称当数据键。

`battlefield-layout.css` 是唯一战场几何权威；原型外观在低优先级`legacy`层内。不得继续在大型CSS尾部追加一轮又一轮`!important`来碰运气。无引用实验模块可由Git历史恢复，不混入当前启动链。

### 3.4 资产与构建

保留战场12分块与结束回合8分块的构建重建、字节数和SHA校验，不手工复制二进制大串、不用损坏文件勉强过构建。发布时要验证浏览器能解码，不能只检查文件头。

结束回合图片缺失/解码失败时，真实按钮文字必须可见且能点击。当前完整机关图仍是过渡资产，本批没有把它伪称为已分离的最终活动核心。

## 4. 坐标与地图V2接口

世界设计平面1152×648。背景和固定机关都通过同一个cover变换绘制；提供worldToScreen/screenToWorld以及可视世界矩形。背景不再单独cover、控件却用另一套contain尺子。

固定机关的图片空间锚点集中在`FIXED_SOCKETS`；CSS读取变量，禁止复制数值到多个文件。当前锚点只是工程过渡接口，地图V2制作前必须按实际屏幕检查共同确认，不能据此声称“新图已经画好”。

敌我战线、英雄、收起手牌属于可视范围内的玩法布局，允许按可视矩形调整，以防宽屏上下裁切吞掉交互。固定石槽与活动部件则必须同坐标绑定，不能各自适配。未来需要固定英雄外壳时，也必须一起制定安全区，不能把响应式英雄直接盖进固定画死的槽。

主要验收横屏：1152×648、1536×691、1400×500、896×414、740×360、1920×1080。竖屏仅作工具/旋转过渡，不宣称完整竖屏战场已制作。超出已验收比例要另测。

## 5. 本批具体整改范围

1. 移除被否决的CSS融合凹槽及镜像补角伪元素；恢复清晰可用的结束回合过渡控件。本批不补画缺角，最终完整外壳资产留地图V2。
2. 建立统一图片平面与明确层级，取消背景/对象各用一套缩放算法。
3. 建立草稿式命令提交和同页单一状态源；移除伪StorageEvent、周期性无意义存档重写及界面独立死亡处理。
4. 合并普通攻击与目标亡语的伤害/死亡管线；补火山之灵击杀潮汐鱼人产生鱼仔的实测回归。
5. 目标弹窗使用与规则同一合法目标列表；目标ID过期、重复选择、目标全部消失不能造成重复结算或死锁。
6. 献祭在固定5格内处理，保留被献祭者亡语产生的衍生物。溢出集合有数据承载，但完整溢出单位交互不是本批新增功能。
7. 旧存档校验与备份回退；旧目标队列和演示效果卡元数据迁移；实际保存异常提示。
8. 构建生成完整离线壳清单，含index与其资源；新壳资源不完整则安装失败，保留旧版本；不删除其他应用缓存，不清空对局。
9. 钉住依赖并提交lock；单元测试、生产构建、完整浏览器验收与部署分开记录。删除误导性的功能完成说明。
10. 已知进化石系列条件尚未实现时明确阻止跳过条件召唤，而不是当成免费卡。此为阻止非法路径，不是擅自实现进化系统。

## 7. 后续总路线及逐阶段验收

### 阶段 B0：工程基线（本批）

交付可追踪源码、依赖锁、单元测试、完整应用浏览器测试、实际截图、验收范围、总计划。停止在地图重制之前。不以“一切无误”覆盖未测设备或未实现功能。

### 阶段 V2：0-7.3 左右一体化战场

先共同确认1152×648母版、原图保留区、左右槽尺寸、裁切安全区、机关核心与遮挡边界。用户明确授权图片生成后，再共同制作左右环境母版。不得每次为单个按钮重画整张地图。

固定环境：左侧空牌槽、承托、金属连接、空数字铭牌；右侧完整四角机关外壳、嵌槽、石材连接。中央战场与现有环境尽量保持原貌。活动层：结束回合核心、文字、牌堆、计数。前景压边按遮挡需要单独导出。

资产必须提供正常/按下需要的活动区域，不在背景里重复烤入亮着的核心或固定牌堆。接入后背景外壳不动，只动活动面板；顶牌能脱离槽口。正式卡背直接复用定版。

验收：左右材质/透视/环境光一致；不存在黑矩形、残留背景、缺角或重复按钮；可用/禁用/按压清楚；固定外壳与核心在各横屏比例中重合；不挤压双方战线。这个阶段完成前不宣称已实现炉石式一体感。

### 阶段 D：0-7.4 动态表现

抽牌以实际规则事件为输入，处理初始8、通常4、后手首次5、技能抽牌、牌库循环，不在动画里写死4张。逐张背面朝上从左槽飞到相应隐藏区/手牌区；交接不泄露对手正面。大量牌最多4层，最后4/3/2/1/0逐层变化。

完善按压、受击、有限环境粒子与减少动态效果模式。规则状态先可靠提交，动画取消/页面切换不得重抽牌、丢牌或锁死按钮。避免所有图片一起缩放当成“机关按入”。

### 阶段 F：0-7.5 战场整体收口

统一亮度、阴影、边缘与工具菜单。测试实际手机横屏/PWA、PC浏览器、持久化、刷新、断网、升级、长手牌、连续回合、暂停/回来。只微调已批准设计，不借“精修”偷换背景或徽记。

### 卡牌正面 A～H

A卡牌结构骨架 → B卡框分层 → C五套基础母版 → D品质/稀有度 → E手牌最终表现 → F战场单位 → G品质动态 → H材质精修。阶段名与战场F收口需明确写前缀，避免串任务。

每一阶段先明确涉及的结构/数据/资产与不做事项。禁止将现有原型完整框图当成最终结构化卡牌完成。先少量代表牌验证长名称、多技能、多属性、数字变化，再批量套用。

### 玩法完善与PC延续

按规则实现矩阵补进化、装备、场景、系列与目标/状态例外，先最小可测规则再接UI。AI对手在稳定合法动作查询上开发，不让AI直接写存档。PC浏览器与手机共享规则层；后续Codex桌面封装不得复制第二份规则引擎。联网不是当前范围。

## 8. 给后续执行者的强制工作方式

- 开始前读本计划、最新验收报告、Git HEAD与差异；既有未提交修改先保护，不凭上一轮文字假定已经部署。
- 先写本批边界和验收条件；需要新资产、用户未授权出图时停止于文字规格，不擅自调用图片工具。
- 状态只通过命令写入；UI不得自己杀随从、补血、调队列、重复注入牌；禁止日志文本驱动规则。
- 改布局进唯一布局文件/几何模块；不要加新全局覆盖文件压过旧文件。动卡牌视觉不得误动战场锚点。
- 先隔离分支、后测试、后合入，严禁不断向main推中间素材试错。二进制必须解码/校验。
- 不能只跑静态按钮页当完整游戏验收；测试真正的手牌拖拽、随从攻击、目标弹窗、热座、保存、缓存。
- 不伪造桌面/手机/联网验证。本地离线DOM适配只能叫诊断；CI真实浏览器也不等于用户手机硬件实测。
- 报告必须写：源提交、涉及文件/模块、运行命令、成功/失败数、截图、未覆盖项、网站是否已更新、下一停止点。
- 当用户否决效果，旧文档“已完成”立即标注作废/被覆盖，不能把旧结论作为拒绝返工的理由。
- 必要时分批保存断点，但不能把“已计划”“已创建文件”“部署成功”写成“效果已验收”。

## 9. 验收门槛与恢复

规则层：原有测试不回退；链式亡语、石化抑制、守护/扣血区别、嘲讽、重复目标、无目标、献祭满场、失败命令不落盘必须覆盖。

界面层：覆盖6种横屏、双方各5个实际随从、实际拖牌/攻击/交接、图片缺失及损坏兜底、目标弹窗跨刷新、真实跨窗口同步。测布局必须用发布构建，不只看源码。

存储与发布：坏主存档可读备份、保存异常不丢当前内存、离线完整壳可启动、新壳安装失败可保留旧壳。清缓存只影响本应用壳，不能清localStorage或其他应用缓存。

main合入前检查未被其他任务推进，使用普通快进/合并，禁止force覆盖。回退用明确revert源提交，不手工重新叠CSS。地图与卡背原始资产保留独立备份，永远不只保留临时会话链接。

**本批之后的下一步仅是左右一体化母版的精确制作规格确认。工程验收不等于新地图已获准生成。**
